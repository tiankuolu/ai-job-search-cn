# 自动搜索与简历投递

在工作台点击“搜索岗位”，选择招聘平台并配置北京实习搜索关键词。程序读取招聘网站完整 JD，按当前个人资料判断岗位匹配。全部导入岗位显示在左侧，公司、岗位名称和申请状态一起保存。匹配意见供用户决定是否申请，各岗位均可生成材料。

选中岗位后，右侧按“岗位分析、编写简历、确认材料、提交申请、查看结果”显示申请过程。点击“生成定制材料”，调用 writer、reviewer 生成与审查申请材料。处理状态显示为一行动画文字，按真实执行阶段更新。

不同岗位可以同时分析、生成材料和导出，默认最多执行三个任务，额外任务排队。批量请求分别建立岗位任务；切换到其他岗位后可以继续生成或编辑该岗位的材料，左侧各岗位分别显示运行标记。同一岗位的生成、编辑、导出和投递互相保护。搜索、登录、投递和结果核查共用招聘浏览器，按顺序执行；搜索遇到正在处理的岗位时保留现有记录。启用搜索后的自动准备时，为已导入岗位分别建立任务。可通过正整数环境变量 `JOBSEARCH_DELIVERY_CONCURRENCY` 调整并发数量。

“添加 JD”支持手动填写和文件导入。文件支持 PDF、Markdown（UTF-8）、PNG、JPEG 与 WebP，单文件不超过 20 MB，PDF 不超过 20 页。图片通过本地 OCR 识别，Markdown 和可读取的 PDF 提取文字，再由当前配置的模型提取公司、岗位名称、地点、招聘链接和平台，以及岗位职责、岗位要求、加分项与其他详情。原文未提供的字段留空。解析结果自动填入可编辑表单，原始正文完整保留；核对后保存到左侧列表。新保存的岗位显示“待分析”；点击“分析 JD”读取个人资料和项目依据。原始文件与解析结果保存在 `runs/delivery/imports/`，提取过程的模型调用记录保存在 `runs/delivery/traces/`，岗位正文及分类详情保存到材料目录和数据库。未关联自动投递平台链接时，可以下载材料并通过招聘方提供的渠道申请。

简历正文必须占用 A4 单页可用高度的 95% 至 100%，目标为 97% 至 99%，最小字号为 9pt。生成过程在真实浏览器中测量排版，根据占用比例补充或精简有依据的正文，再次审查内容与版面后导出。占用未达标的材料无法自动投递。

通过审查的材料继续生成结构化简历，再次审查事实与表达，使用 ASu 模板生成可编辑 HTML，由本机 Edge 导出 A4 单页 PDF，核对正文、页面边界、链接、字号和页面占用，导出 PNG 图片。

确认材料页面直接展示 HTML 简历，点击文字即可修改，也可放大编辑。修改自动保存到服务端，刷新后恢复；切换岗位或步骤时会等待当前修改保存。每次保存保留原文件与上一份材料记录。点击“确认材料，继续”会根据当前 HTML 重新生成 PDF 和图片，检查单页、95% 至 100% 页面占用、最小字号、正文完整性、教育 GPA、链接与边界，再进入投递确认。检查失败时保留编辑内容和错误提示，可以继续修改后重新导出。

修改尚未重新导出时，PDF 下载与投递接口会阻止使用旧文件。发送前核对 HTML、PDF 和图片的内容摘要与导出版本。已投递及待核实的材料只供查看。打招呼语支持修改保存，较多内容修改仍可填写要求并重新生成材料。确认材料后检查对应平台登录状态，点击“确认并投递”发送当前岗位材料。查看结果步骤显示已投递或发送结果待核实。

平台选择包含 BOSS、猎聘、牛客和实习僧。四个平台均可读取岗位并使用原有 Agent 准备定制材料；BOSS 与猎聘已经完成文字和图片简历的真实发送验证。牛客与实习僧的投递入口由服务端能力状态控制，实际提交流程仍待授权验证。

教育背景与 GPA 从当前候选人资料读取。结构化数据由程序核对学校与 GPA 的对应关系，PDF 编译后再次核对正文中的 GPA。

## 运行

招聘浏览器服务需要提供兼容的 `/api/jobsearch/*` 接口。`start-integrated.ps1` 从本项目目录解析 `../../get_jobs` 作为服务源码目录；安装时核对该路径与实际目录。Java 21、Gradle、已安装的 Chrome 或 Edge、Python 3.11、Playwright、Poppler 和 Node.js 为实际依赖。

该服务需要提供浏览器登录状态、公开岗位读取、指定岗位原文、材料发送和结果回执接口，并使用 `X-Jobsearch-Token` 校验本地请求。当前仓库通过 HTTP 调用该服务；安装完整招聘流程时需要同时提供具有这些接口的适配服务源码和发行版数据库。

在本项目目录安装 `requirements-web.txt`。通过下面的命令配置实际程序位置：

```powershell
py -3.11 tools/setup_delivery.py --java-home '<Java 21 根目录>' --gradle '<gradle.bat 路径>' --browser-channel msedge --pdftoppm '<pdftoppm.exe 路径>'
.\start-integrated.ps1 -Build
```

首次运行前将 get_jobs 发行版提供的空数据库保存为服务源码目录中的 `db/getjobs.db`。模型配置使用已有 `JOBSEARCH_LLM_*`，继续读取候选人资料与基版。Java 浏览器服务监听 `127.0.0.1:9527`，求职工作台监听 `127.0.0.1:8765`。

通过 `JOBSEARCH_LLM_*` 配置模型。使用 DeepSeek 配置文件时，设置 `JOBSEARCH_DEEPSEEK_ENV_FILE`，程序从中读取 `DEEPSEEK_BASE_URL` 与 `DEEPSEEK_API_KEY`。密钥保留在本地配置中。岗位匹配和结构化简历生成启用模型的 JSON Output，随后使用 Pydantic 校验字段。

通过“平台与设置”选择平台并打开对应登录浏览器，完成扫码与平台要求的验证，然后检查登录状态。发送操作由“确认并投递”按钮启动。

使用平台账号前检查自动打招呼设置，保证发送当前岗位对应且已经确认的文案。

## 记录与恢复

- 抓取的岗位原文保存到材料目录 `岗位记录/inbox/<平台英文名大写>-<id>.md`；已经存在的正文保留当前内容。
- 搜索来源、匹配结果、材料版本和任务状态保存到 `runs/delivery/state.sqlite`。
- PDF、图片、简历源文件、结构化正文与打招呼语保存到 `runs/delivery/packages/<package_id>/`。
- 模型调用继续保存在原有 `runs/`，申请包继续保存到材料目录 `岗位记录/evaluated/`。
- Java 服务在 `data/integration/<operation_id>/` 保存实际聊天截图与发送结果。
- 只有文字和图片均确认发送后，更新材料目录 `delivery-status.csv`；发送失败、中断或超时保留“发送结果待核实”，禁止自动重复发送。

已有沟通记录的招聘者会停止自动联系，保留人工核对。同一公司与同名岗位的发送记录也会阻止跨平台重复投递。简历文件变化会阻止发送，需要重新生成与检查。
